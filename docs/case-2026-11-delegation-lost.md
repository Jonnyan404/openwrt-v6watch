# 案例：一切正常，但 IPv6 一个包都出不去

> 2026-11-11，ImmortalWrt 25.12.2（mediatek/filogic），无线 STA 上行。
> 这份记录是 `v6watch` 的判定逻辑的来源——`delegation_lost` 这一档不是想出来的，是撞出来的。

## 现象

用户描述："v6 又不通了，重启一下 v6 接口就好，但过几天又断。"

| 项目 | 状态 |
|---|---|
| IPv4 | 正常，延迟 7ms |
| 上游网关 `fe80::1` | 可达，2.8ms |
| 接口地址 / 前缀 / 默认路由 / NDP 邻居 | 全部存在，lifetime 未过期且在续期 |
| 出站 IPv6 | 100% 丢包 |

配置层面找不到任何问题。这就是这类故障最气人的地方：**所有面板都绿，就是上不了网。**

## 拓扑

```
wwan (phy0-sta0, 192.168.1.5/24)  ──STA──▶  上游 AP "302"
  └ wwan6 = DHCPv6
       ├ IA_NA : 2408:820c:9c39:8280::1/128
       ├ SLAAC : 2408:820c:9c39:8280:82af:caff:fe83:3c61/64
       └ PD    : 2408:820c:9c39:8284::/62  →  br-lan
```

## 分层的排查过程

关键在于**不要一上来就改配置**，而是从下往上每一层都问一句"这层通吗"：

```
1. 链路层   ping6 -I phy0-sta0 fe80::1              → 通 2.8ms
2. 邻居层   ip -6 neigh | grep 9284                  → REACHABLE
3. 路由层   ip -6 route show default                 → 3 条 from 限定默认路由，正常
4. 出站层   ping6 2400:3200::1                       → 100% 丢
```

到第 4 层就卡住了：前三层都好，为什么出不去？

于是换了个问法——**换个源地址再试**：

```bash
# 用 DHCPv6 分配的 IA_NA 地址作源
ping6 -I 2408:820c:9c39:8280::1        2400:3200::1   → 100% 丢
# 用 PD 前缀里的地址作源
ping6 -I 2408:820c:9c39:8284::1        2400:3200::1   → 100% 丢
# 用 SLAAC 自动配置的 /64 地址作源
ping6 -I 2408:820c:9c39:8280:82af:...  2400:3200::1   → 3/3 通
```

**这就是分水岭。** 同一个目标、同一时刻、同一个接口，只换源地址，结果从 100% 丢包变成 0% 丢包。

包确实发出去了（`ping6` 没有报 `Network unreachable`，只报丢包）。所以问题不在本机：

> 上游只放行**直连 /64 前缀**的源地址，不认**委派给这个客户端**的 IA_NA 地址和 PD 前缀。

回头看日志，答案写在 24 小时前：

```
11-09 17:12  netifd: Interface 'wwan6' has lost the connection
11-09 17:12  netifd: Interface 'wwan6' is now up
11-10 10:47  wwan6: Server returned IA_NA status 'No Binding'
11-10 10:47  wwan6: Server returned IA_PD status 'No Binding'
11-11 11:19  （ifup wwan6）→ 恢复
```

`'No Binding'` 是 DHCPv6 服务器在说：**我不认识这个客户端**。上游重启或清表之后，它把「这个客户端的 ::1/128 和 8284::/62 该往哪送」的转发表项丢了。

而客户端这边，odhcp6c 仍然拿着旧租约继续 renew，地址 lifetime 一直在刷新（`valid_lft` 从 41h 涨到 65h），看起来"租约有效"。**双方状态已经脱节，但没有任何一方报错。**

## 为什么重启接口就好了

`ifup wwan6` 会让 odhcp6c 从头走一遍 Solicit → Advertise → Request → Reply，上游趁机重建绑定和转发表项。实测 12 秒内所有源地址都恢复，包括 PD 源和境外 v6。

顺带一个好消息：因为 odhcp6c 带了 `-P0:da412400` 前缀提示，re-DHCPv6 拿到的 PD 是同一个 `8284::/62`，所以 LAN 客户端的地址不会变，代价很小。

## 为什么这不是"PD 丢失"

第一反应通常是"PD 掉了，重拨"。但看故障时刻的 `ubus status`：

```json
"ipv6-prefix": [{
  "address": "2408:820c:9c39:8284::", "mask": 62,
  "valid": 147878, "preferred": 61478,
  "assigned": { "lan": { "address": "2408:820c:9c39:8284::", "mask": 62 } }
}]
```

**PD 在、lifetime 在刷新、`br-lan` 上的地址也在。** `ifup` 前后前缀一个字节都没变。

这个区别有实际后果：如果按"PD 丢失"写判据（检测前缀消失或变化就重拨），**这次故障一次都不会触发**，因为 PD 好得不能再好。判据必须落在「出站到底通不通」上。

## 普通看门狗在这个场景里的三个坑

市面上最常见的实现是：ping 一组目标 → 全失败 N 次 → `ifdown/ifup` 接口。逻辑本身对，但缺三样东西：

1. **不区分故障形态**。无线掉了、上游断电、运营商关了 v6、委派失效——一律重启接口。第一种和第三种情况下重启纯属折腾。
2. **重启后不复查**。`sleep 15` 就结束，成没成不知道，也不记录。
3. **没有冷却和退避**。计数清零后回到循环。如果运营商那天真的关了 IPv6，它会**每十几分钟重启一次，永远不停**——每次还顺手 reload 防火墙、让 LAN 客户端的 PD 前缀抖一下。

`v6watch` 的 `egress_down` 这一档就是为了第 3 条存在的：判定为"上游可达但出口整体不通"时**默认只告警、不重启**，因为这时候重启接口解决不了任何问题。

## 可复用的结论

如果你遇到"IPv6 面板全绿但上不了网"：

```bash
# 一条命令看出是哪种故障
ping6 2400:3200::1                              # 默认源
ping6 -I $(ip -6 -o addr show dev <dev> scope global | awk '$4~/\/64$/{sub(/\/64$/,"",$4);print $4;exit}') 2400:3200::1
```

- 两个都通 → 没问题
- 默认源不通、/64 源通 → **委派失效**，重启接口（`ifup <iface>`）能好
- 两个都不通但网关可达 → 上游/运营商侧问题，重启没用
- 网关都不通 → 链路断了，等它自己恢复

还有一个容易误判的地方：在这类配置上，`ip -6 route get <公网v6>` 经常返回 `Network unreachable`，因为 netifd 只装 source-specific 默认路由（`default from <前缀> via ...`），从来不装裸 default。**这是常态，不是故障**，别据此下结论。
